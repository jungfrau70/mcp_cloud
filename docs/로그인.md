# MentorAi 플랫폼 로그인 및 접근 제어

## 1. 개요
MentorAi 플랫폼의 사용자 로그인 및 접근 제어는 **Authelia**를 기반으로 한 강력한 **역할 기반 접근 제어(RBAC)** 시스템을 통해 이루어집니다. 사용자는 역할에 따라 플랫폼 내에서 접근할 수 있는 기능과 데이터가 달라집니다.

## 2. 인증 (Authentication)

*   **주요 담당:** Authelia (Identity Provider, IdP)
*   **지원 방식:** 이메일/비밀번호 기반 로그인, 2단계 인증(2FA), 소셜 로그인 (Google 등).
*   **정보 전달:** Authelia는 인증 성공 후 사용자 정보를 백엔드로 `X-Forwarded-Email`, `X-Forwarded-Groups` 등의 HTTP 헤더를 통해 전달합니다.

## 3. 인가 (Authorization)

*   **주요 담당:** FastAPI 백엔드
*   **제어 방식:** Authelia로부터 전달받은 `X-Forwarded-User/Groups` 헤더를 기반으로 사용자 역할을 (학생, 튜터, 관리자) 도출하고, 각 역할에 따른 접근 권한을 강제합니다.
*   **접근 제어 정책 (예시):**
    *   **커리큘럼 (`/textbook` 경로):** 일반 회원도 열람 가능 (Bypass 정책 적용).
    *   **지식 베이스 화면 (`/knowledge-base*`) 및 관련 API (`/api/v1/knowledge-base/*`):** 관리자만 접근 가능 (Authelia의 `one_factor` 정책 및 FastAPI RBAC 가드 적용).
*   **다중 방어:** Nginx Proxy Manager(NPM)의 Forward Auth, Authelia의 `access_control` 설정, FastAPI 백엔드의 RBAC 가드를 통해 3중으로 접근 제어가 적용됩니다.

## 4. 사용자 로그인 절차

1.  **로그인 요청:** 사용자는 Authelia 로그인 페이지를 통해 이메일/비밀번호 또는 소셜 계정으로 로그인을 시도합니다.
2.  **인증 처리:** Authelia가 사용자 자격 증명을 확인하고, 성공 시 사용자의 역할 정보가 포함된 인증 토큰(예: JWT)을 발급합니다.
3.  **헤더 전달:** Authelia는 인증된 사용자 정보를 `X-Forwarded-Email`, `X-Forwarded-Groups` 등의 HTTP 헤더에 담아 백엔드로 요청을 프록시합니다.
4.  **JIT (Just-In-Time) 프로비저닝:**
    *   백엔드(`api/v1/users/me` 엔드포인트)는 전달받은 헤더를 기반으로 사용자를 식별합니다.
    *   **신규 사용자:** 데이터베이스에 존재하지 않는 사용자일 경우, 첫 방문 시 자동으로 사용자 계정을 생성하고 기본 역할(학생)을 부여합니다.
    *   **기존 사용자:** 이미 존재하는 사용자일 경우, `last_login_at`을 업데이트하고, Authelia에서 전달받은 그룹 정보에 따라 역할(예: `admins` 그룹에 속하면 `admin` 역할)을 업데이트합니다.
5.  **UI 렌더링:** 프론트엔드는 백엔드로부터 받은 사용자 역할 정보에 따라 학생용 대시보드 또는 튜터용 대시보드를 표시하는 등 UI를 다르게 렌더링하여 개인화된 경험을 제공합니다.

## 5. 사용자 인증/인가 시나리오 (User Authentication/Authorization Scenarios)

다음은 MentorAi 플랫폼에서 발생할 수 있는 주요 사용자 인증 및 인가 시나리오입니다.

### 5.1. 신규 학생 로그인 및 JIT 프로비저닝
1.  **사용자 접근:** 신규 학생이 MentorAi 플랫폼에 처음 접근합니다.
2.  **Authelia 리디렉션:** 플랫폼은 Authelia 로그인 페이지로 사용자를 리디렉션합니다.
3.  **로그인:** 학생은 이메일/비밀번호 또는 소셜 계정(예: Google)으로 Authelia에 로그인합니다.
4.  **Authelia 인증 및 헤더 전달:** Authelia는 학생을 성공적으로 인증하고, `X-Forwarded-Email` (학생 이메일) 및 `X-Forwarded-Groups` (예: `student` 그룹) 헤더를 포함하여 백엔드로 요청을 프록시합니다.
5.  **백엔드 JIT 프로비저닝:** 백엔드의 `/api/v1/users/me` 엔드포인트는 전달받은 헤더를 확인합니다. 해당 이메일을 가진 사용자가 데이터베이스에 없으므로, 새로운 사용자 계정을 생성하고 기본 역할인 `student`를 부여합니다.
6.  **프론트엔드 렌더링:** 백엔드로부터 받은 역할 정보에 따라 프론트엔드는 학생 대시보드를 렌더링합니다.

### 5.2. 기존 관리자 로그인 및 보호된 리소스 접근
1.  **관리자 접근:** 기존 관리자가 지식 베이스와 같은 보호된 리소스(`knowledge-base` 경로)에 직접 접근을 시도합니다.
2.  **Authelia 인증 (필요시):** 관리자가 이전에 로그인하지 않았다면, Authelia 로그인 페이지로 리디렉션됩니다. 로그인 후 Authelia는 `X-Forwarded-Email` 및 `X-Forwarded-Groups` (예: `admins` 그룹) 헤더를 백엔드로 전달합니다.
3.  **백엔드 JIT 프로비저닝 (업데이트):** 백엔드의 `/api/v1/users/me` 엔드포인트는 전달받은 헤더를 확인합니다. 기존 관리자이므로 `last_login_at`을 업데이트하고, `admins` 그룹에 속하므로 역할이 `admin`으로 유지되거나 업데이트됩니다.
4.  **FastAPI RBAC 가드:** 지식 베이스 API (`/api/v1/knowledge-base/*`)에 적용된 `get_current_admin_user` 의존성이 `X-Forwarded-Groups` 헤더에서 `admins` 그룹을 확인하고 접근을 허용합니다.
5.  **프론트엔드 렌더링:** 프론트엔드는 지식 베이스의 관리자 뷰를 렌더링합니다.

### 5.3. 학생이 관리자 전용 리소스에 접근 시도
1.  **학생 접근:** 학생이 로그인한 상태에서 지식 베이스와 같은 관리자 전용 리소스(`knowledge-base` 경로)에 접근을 시도합니다.
2.  **Authelia 헤더 전달:** Authelia는 학생의 `X-Forwarded-Email` 및 `X-Forwarded-Groups` (예: `student` 그룹) 헤더를 백엔드로 전달합니다.
3.  **FastAPI RBAC 가드:** 지식 베이스 API에 적용된 `get_current_admin_user` 의존성이 `X-Forwarded-Groups` 헤더를 확인합니다. `admins` 그룹이 없으므로 `HTTPException` (403 Forbidden)을 발생시킵니다.
4.  **프론트엔드 처리:** 백엔드로부터 403 응답을 받은 프론트엔드는 접근 거부 메시지를 표시하거나, 권한이 없는 페이지로 리디렉션합니다.
